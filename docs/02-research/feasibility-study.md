# Feasibility study

_Semester 1 evidence that this project can be completed to its stated
aim within the time, compute and access actually available._

This file is the evidence base for Section 6 of D1 and for the
Preparation and Feasibility Video (D2). Each section answers one thing a
marker has to be able to check: that the preparation was real, that the
choices were made against alternatives rather than by default, that the
feasibility claim rests on measurements rather than assertion, that the
plan survives contact with its dependencies, that the risks are scored
rather than listed, that the professional, legal, ethical and social
ground is covered, and that success has been defined in advance.

Every figure below is traceable. Experimental numbers come from rows in
`results/results.csv`, each of which carries the commit hash, the random
seed and the condition that produced it. Timings come from the run logs
referenced in the issue that produced them.

> **Regeneration note.** Rows tagged `synthetic_human` /
> `synthetic_machine` come from the stand-in corpus that `make demo`
> generates, and exist so the pipeline can be demonstrated with no
> download. The corpus-level figures in §3 come from runs on the real
> corpora and are regenerated by `make data && make experiments`. Do not
> quote a number from this file that the current `results.csv` does not
> contain.

## 1. Preparation: what was done before anything was claimed

Feasibility was not assumed in Week 3 and confirmed in Week 11. The
order of work was chosen so that the things most likely to make the
project impossible were tested first.

| Week | Preparation step | What it settled | Issue |
|---|---|---|---|
| W2–W3 | Dataset survey: eight candidate corpora screened on availability, licence, label provenance and size | Only two corpora carry both populations of fake review with defensible labels and a licence that permits research use | #4, #5 |
| W3 | Licence and terms-of-service check on every candidate | Live scraping ruled out before any code was written; recorded as out-of-scope requirement W1 | #2 |
| W4 | Both corpora downloaded, checksummed, provenance recorded | The data exists, is obtainable, and is the version reported on | #5 |
| W4 | Local transformer load attempted | `roberta-base` does not fit in laptop memory — this is the constraint the whole model plan bends around | #43 |
| W4–W5 | Preprocessing pipeline built **before** any model | One command regenerates every split; determinism covered by a test | #13 |
| W5 | Leakage bug found and fixed: vectoriser was fitted before the split | Every score before this point was inflated; the fix is now guarded by a test | #7 |
| W5–W6 | Three classical baselines run under one protocol | The comparison is expressible at all | #7, #15, #16 |
| W6 | First cross-dataset test | The finding the project turns on — pulled forward deliberately, because a feasibility study that discovers its central result in Week 10 has not been planned | #24 |
| W7 | Transformer fine-tuned on a free T4 | The compute constraint has a working answer, measured not assumed | #43 |
| W7 | Two tool spikes (MLflow, DVC) run and abandoned | Tracking solved with an append-only CSV plus commit hashes | — |
| W9 | Reproduction from a clean clone on a second machine | The reproducibility claim is tested, not asserted | #38 |

The pattern is deliberate: **every step that could have killed the
project was attempted in the first half of the semester**, when there
was still time to re-scope. Nothing structural was discovered after
Week 7.

### What was tried and abandoned

Recording the discards is part of the evidence; a preparation section
that lists only successes is a sales document.

- **MLflow** — half a day. Real value at team scale; for one student it
  added a server to keep alive and a second source of truth about what
  ran. Dropped.
- **DVC** — half a day. Solves dataset versioning, which this project
  does not have: the corpora are fixed published releases identified by
  checksum. Dropped.
- **Git LFS** — evaluated for committing the corpora. Rejected on
  licence grounds first (neither corpus should be redistributed) and
  quota grounds second.
- **SMOTE oversampling** (#44) — two days, negative result, kept in the
  report as the evidence for not resampling.

A rule came out of the second discard and has held since: **at most half
a day evaluating a new tool before deciding.**

## 2. Methods and tools, justified against alternatives

The rubric asks for justification against alternatives, so each row
names what was rejected and why. A choice with no rejected alternative
is a default, not a decision.

### 2.1 Text representation

| Option | Considered because | Rejected / chosen because |
|---|---|---|
| Raw term counts (bag of words) | Simplest possible baseline | **Rejected.** Length-dominated; TF–IDF costs nothing extra and normalises it |
| **TF–IDF word n-grams (1,2)** | Standard for this task since Ott et al. (2011) | **Chosen.** Directly comparable with the literature the project measures itself against |
| **TF–IDF character n-grams (3,5), `char_wb`** | Hypothesis: character patterns survive distribution shift better than vocabulary | **Chosen** as a second vectoriser in every condition (#27). Tests the hypothesis rather than assuming it |
| Static embeddings (word2vec, GloVe, fastText) | Cheap, well understood | **Rejected.** Averaged embeddings lose the surface cues (punctuation, superlatives, exclamation density) that deception detection leans on, and add a download dependency for no expected gain |
| **Fine-tuned transformer representations** | The current state of the art | **Chosen** as one arm (#43), not as the whole project — see 2.3 |

### 2.2 Classifier

| Option | Rejected / chosen because |
|---|---|
| **Logistic regression** | **Chosen.** Fast, calibrated, coefficients inspectable — which matters for Objective 4 in Semester 2 |
| **Linear SVM** | **Chosen.** The strongest classical baseline on this task in the literature; different inductive bias from LR |
| **Random forest** | **Chosen.** Non-linear contrast; also the model most likely to overfit corpus artefacts, which makes it informative in the cross-dataset condition |
| Gradient boosting (XGBoost, LightGBM) | **Rejected.** Adds a dependency and a hyperparameter surface without adding a distinct inductive bias to the comparison. Half a day of tuning buys less than the same half day spent on the transfer question |
| Naive Bayes | **Rejected.** Would be a fourth classical point on the same curve |

### 2.3 Transformer

| Option | Params | Rejected / chosen because |
|---|---|---|
| `roberta-base` | 125 M | **Rejected on measurement.** Would not load on the available laptop (R2, W4) |
| `bert-base-uncased` | 110 M | **Rejected.** Same memory profile; RoBERTa's pre-training is the stronger starting point for this task |
| `deberta-v3-base` | 184 M | **Rejected.** Better results reported, larger memory and slower — the wrong trade for a feasibility study on free compute |
| **`distilroberta-base`** | 82 M | **Chosen.** Fits the memory budget, fine-tunes in minutes on a free T4, and keeps the comparison honest because every classical model runs on the same splits |

The point is not that `distilroberta-base` is the best available model.
It is that the constraint (R2) was measured in Week 4 and the model
choice follows from the measurement, which is what makes the Semester 2
plan credible rather than aspirational.

### 2.4 Evaluation

| Decision | Alternative rejected | Reason |
|---|---|---|
| **Macro-F1 as the headline metric** | Accuracy | Raised by the supervisor on 29 Oct: the splits are not exactly balanced, and accuracy hides per-class collapse — which is precisely the failure mode expected in the cross-dataset condition (#17) |
| Per-class precision/recall + confusion matrix on every run | Headline metric only | A single number cannot show *which* class transfers |
| **Stratified 5-fold CV within corpus** | Single 70/15/15 holdout | A holdout on 1,600 documents gives an unstable estimate; five folds support a confidence interval |
| | Leave-one-out | Computationally pointless at this corpus size for a negligible variance gain |
| **Confidence intervals, not significance tests, in Semester 1** | McNemar's test now | Dietterich (1998) is the right instrument, but it answers a Semester 2 question. Descoped 5 Nov; recorded, not dropped (#45) |
| **Class weights available, resampling rejected** | SMOTE | Tested (#44). Macro-F1 fell. Rejecting it on measured evidence is stronger than never trying it |

### 2.5 Engineering and management tooling

| Decision | Alternative rejected | Reason |
|---|---|---|
| scikit-learn `Pipeline` with the vectoriser as step 1 | Vectorise once, then split | Leaks test vocabulary and inflates every score; cost a day in W5 and is now guarded by a test (#7) |
| Append-only `results.csv` + commit hash + seed | MLflow, DVC | Half-day spikes, both dropped: single-student project, fixed datasets. Every number in D1 traces to a row and a commit |
| GitHub Issues + Projects board + milestones | Jira, Trello, a spreadsheet | The issues live next to the code that closes them, and the dated open/close record is the D4 evidence |
| Free Colab T4 | Paid GPU, university cluster, laptop-only | No budget (constraint); cluster access not available to undergraduates on this programme; laptop ruled out by R2 |
| GitHub Actions CI on committed fixtures | No CI; CI over real data | Real data is git-ignored, so CI must run on fixtures — this is why the first two CI runs failed (#31) |

## 3. Feasibility evidence

Four independent kinds of evidence, because a feasibility claim resting
on one is a claim resting on none.

### 3.1 Prototype: the pipeline runs end to end

`make demo` generates the stand-in corpus, runs every model in every
condition, appends rows to `results/results.csv` with the commit hash,
writes the figures, and trains the CLI — with **no network access**.
This is what is demonstrated live in D2, and it is what lets CI run at
all.

```
make demo
python -m frd.cli predict "Absolutely the best hotel ever, five stars is not enough!!"
```

Verified from a clean clone on a second machine (#38): 28 tests pass,
`ruff` clean, experiments reproduce.

### 3.2 Pilot results: the comparison is expressible

The experimental design produces the rows the research question needs —
within-corpus, both cross-corpus directions, and pooled training —
under one protocol, one seed and one metric.

| Condition | What it establishes | Rows in `results.csv` |
|---|---|---|
| Within-corpus, 5-fold CV | Each detector is competent on its own population, and in line with published figures | per model × vectoriser × corpus |
| Cross-corpus, both directions | Whether detection transfers between human-written and machine-generated fakes — **the project's question** | per model × vectoriser × direction |
| Combined training | Whether pooling narrows the gap | per model × vectoriser × held-out split |

The feasibility claim is **not** that the scores are high. It is that
all three conditions run under identical conditions, so the difference
between them means something. A cross-dataset drop is a result; an
unrunnable comparison would have been the failure.

### 3.3 Benchmarks: measured compute, not estimated

| Measurement | Value | Source |
|---|---|---|
| `roberta-base` load on laptop | fails — out of memory | R2, W4 |
| `distilroberta-base` fine-tune, small corpus, free T4 | ~12 min wall clock including model download | R2 closure, W7 (#43) |
| Full classical sweep (3 models × 2 vectorisers × 3 conditions) on laptop CPU | minutes, not hours | `make experiments` |
| `make demo` end to end | under 2 min | D2 recording |
| Test suite, no network | 28 tests | #48 |

### 3.4 Calculations: does the budget close?

**Compute.** A fine-tune pass is `ceil(0.85 · N / batch) · epochs` optimiser
steps. At batch 16, 3 epochs, max sequence length 256, and the ~3 steps/s
measured on a free T4:

| Corpus | N | Steps | Est. GPU time |
|---|---|---|---|
| Small human-written corpus (~1.6 k) | 1,600 | ~255 | ~2 min + download |
| Large machine-generated corpus (~40 k) | 40,432 | ~6,450 | ~36 min |
| Both, plus cross-direction evaluation | — | — | **≈ 1.5 h** |

Semester 2 adds a second generator corpus, a third corpus and ablations:
budget **≈ 10 h of T4 time across the semester**. A free Colab session
provides several hours of T4 per day, so the requirement is roughly one
afternoon's allocation spread over twelve weeks. Checkpointing is on, so
a session cut short resumes rather than restarts (R8).

**Memory.** The binding constraint is the character n-gram matrix, not
the model. For the large corpus at `char_wb` (3,5), roughly 40 k
documents × ~700 non-zero features ≈ 2.8 × 10⁷ non-zeros ≈ **340 MB** as
a sparse float matrix — comfortable on an 8 GB laptop, and the reason
the vectoriser lives inside the pipeline rather than being materialised
once for the whole corpus.

**Time.** The project is budgeted at ~400 hours across two semesters.

## 5. Risk, quantified

The Semester 1 register (`docs/01-planning/risk-register.md`) scored
likelihood and impact as High/Medium/Low. That is adequate for tracking
but it cannot be added up, so it is restated here numerically:
**P** is probability (0–1), **impact** is project days lost if it lands
(one project day ≈ 4 working hours alongside other coursework), and
**exposure = P × impact**.

| ID | Risk | P | Impact (d) | Exposure (d) | Trigger to watch | Mitigation | Contingency path | Status |
|---|---|---|---|---|---|---|---|---|
| R1 | Restricted platform data (Yelp) not granted | 0.70 | 6 | 4.2 | No reply within 3 weeks | Semester 1 uses the two secured corpora | Amazon Reviews 2023 | **Closed** by descoping, W10 |
| R2 | Insufficient compute to fine-tune a transformer | 0.80 | 5 | 4.0 | Model fails to load locally | Free T4, `distilroberta-base`, shorter sequences | Classical-only comparison | **Closed** W7, 12-min run |
| R3 | Ethics approval not returned in time | 0.15 | 10 | 1.5 | No acknowledgement within 2 weeks | Submitted 28 Oct, 2 days early | No Semester 1 work depends on the return | **Closed** W7 |
| R4 | D1/D2 collide with other coursework | 0.80 | 8 | 6.4 | Two deadlines land in the same week | Experiments front-loaded W4–W7; internal deadlines 1 week early | Week 11 reserved for revision only | **Closed** W10 |
| R5 | Results not comparable with published figures | 0.60 | 4 | **2.4** | A reviewer asks "compared with what?" | Report conditions separately; state corpus, split and seed on every row | Limitations section states what the numbers cannot support | **Open**, managed |
| R6 | Semester 2 evaluation needs an ethics amendment | 0.25 | 12 | **3.0** | Amendment not acknowledged by Week 3 | Drafted over the break, submitted Week 1 | Pilot with classmates under existing approval | **Open** |
| R7 | A dataset source is withdrawn or revised | 0.10 | 7 | **0.7** | Checksum mismatch on re-download | SHA-256 recorded; offline copy retained | Report from the checksummed copy | **Open** |
| R8 | Free GPU quota exhausted mid-run | 0.35 | 2 | **0.7** | Session terminated before the final epoch | Checkpointing enabled | Resume, or switch provider | **Open** |

**Residual exposure on open risks: ≈ 6.8 project days ≈ 27 hours.**
That number is what the 28-hour Semester 2 contingency buffer in §3.4 is
sized against, and it is the one calculation in this document that ties
the risk register to the plan.

Two risks were considered and deliberately **not** registered: losing
work (GitHub, a local clone and an external-drive copy already cover it)
and supervisor unavailability (a fortnightly slot agreed in Week 3, with
email answered within a day throughout). Registering either would be
theatre, and a register padded with non-risks is harder to act on.

### Risks that materialised

**R2 landed immediately** — `roberta-base` would not load in Week 4 — and
was closed in Week 7. It mattered more than it first looked: D2 has to
demonstrate that the Semester 2 plan is achievable with the compute
actually available, so an unresolved R2 would have undermined the video,
not merely an experiment.

**R4 was the one to watch and did not bite**, because the mitigation was
in place from Week 3. Other coursework did cluster in Weeks 8–10 as
predicted; the experimental work had already been front-loaded, leaving
writing, which slices into short sessions far better than debugging does.

## 6. Professional, legal, regulatory, ethical and social considerations

### Professional
Conducted under the BCS Code of Conduct and the ACM Code of Ethics. The
two clauses that bind hardest here are **competence** — not claiming
more than the evidence supports, which is why §3.2 states what the
feasibility results do *not* establish — and **public interest**, which
is why the social section below is not boilerplate. All work is the
student's own; every third-party dataset, library and paper is cited,
and AI assistance is declared per programme policy.

### Legal and regulatory
- **Data protection.** No personal data is processed. Both corpora are
  published research datasets of review text carrying no names, contact
  details or account identifiers. Reviews are used as text, never linked
  to individuals, and no re-identification is attempted. On that basis
  UK GDPR / GDPR obligations are not engaged; the position is recorded
  rather than assumed.
- **Licensing.** Each corpus is used under the licence it was published
  with, recorded per file in `data/README.md` alongside its SHA-256.
  Neither corpus is redistributed — the repository downloads on demand.
  This is also why Git LFS was rejected.
- **Terms of service.** Live collection from a review platform was
  considered at the first supervision meeting and rejected on
  terms-of-service and ethics grounds *before any code was written*.
  Recorded as out-of-scope requirement W1.
- **Third-party code.** All dependencies are permissively licensed and
  pinned; the model weights are used under their published terms.

### Ethical
Approved as low-risk, secondary-data-only (submitted 28 Oct, Week 7). No
participants in Semester 1. Datasets and trained models stay off version
control. The Semester 2 demonstrator evaluation needs an amendment
(R6), drafted over the break: participant information sheet, written
consent, pseudonymous storage, retention to the end of the assessment
period, recruitment without incentive or coercion.

**Dual use.** A detector can in principle be probed to learn what evades
it. The mitigation is proportionate to a student project: no
adversarial-evasion experiments, and release as a research artefact with
a model card stating its limitations — not as a service. The project
detects deceptive text; it does not produce it, and the
machine-generated corpus is an existing published dataset rather than
newly generated text.

### Social
Three consequences worth stating, because a detector is not a neutral
object once it leaves the repository.

1. **False positives fall on people, not on spam.** A wrongly flagged
   review costs an honest reviewer their voice and can cost a small
   business its rating. This is the argument for reporting per-class
   precision and recall rather than a single headline number: the cost
   of the two error types is not symmetric, and the marker should be
   able to see which one the model makes.
2. **Fluency-based detection is biased against non-native writers.**
   Liang et al. (2023) showed GPT detectors misclassify non-native
   English writing at a much higher rate, because low perplexity and
   limited vocabulary look like machine text. The corpora here are
   English-only and largely native-written, so this project cannot
   measure that bias — which is exactly why the limitation is stated
   rather than left implicit, and why the model card will carry it.
3. **The generalisation gap is the social finding, not a technical
   footnote.** A platform deploying a detector trained on one population
   of fake reviews against the other would be making decisions about
   real businesses on a model measured in the wrong setting. That is the
   practical reason this project's negative result is worth reporting.

## 7. Success criteria, defined and argued

Defined at the outset and not revised to fit the results. Each is stated
so that it can be checked by someone who did not run it.

### Semester 1

| # | Criterion | Test | Met? |
|---|---|---|---|
| S1 | **Reproducible.** A third party can clone the repository and regenerate the reported results | Clean clone on a second machine, README followed line by line (#38) | Yes |
| S2 | **Traceable.** Every reported number ties to code | Each `results.csv` row carries commit hash, seed and condition | Yes |
| S3 | **Comparable.** All models evaluated on identical splits under one metric | Vectoriser inside the CV fold; macro-F1 with per-class metrics on every run (#17) | Yes |
| S4 | **The question is answerable.** Both cross-corpus directions run and reported with intervals | Rows for both directions plus combined training (#24, #25, #26) | Yes |
| S5 | **Within-corpus performance in line with the literature** | Comparable with the ~0.90 accuracy Ott et al. (2011) report on the same corpus | Yes |
| S6 | **Delivered.** Ethics, D1 and D2 submitted on time | Ethics 28 Oct (deadline 30th); D1 and D2 24 Nov (deadline 26th) | Yes |

### Semester 2

| # | Criterion | Test |
|---|---|---|
| S7 | Demonstrator classifies a pasted review in under 2 s on laptop CPU | Timed on the target machine |
| S8 | User evaluation with 8–10 participants under an approved amendment | Ethics approval plus completed sessions |
| S9 | The transfer finding is tested across *generators*, not only across corpora | A second machine-generated set (#37) |
| S10 | Model-pair differences tested for significance | McNemar per Dietterich (1998) (#45) |

### The argument

**Success is not defined as a high detection score, and this is the
point of the whole design.** A project whose success criterion was
"macro-F1 above 0.95" would be satisfied by training and testing on one
corpus — which is exactly the practice the literature review identifies
as the field's blind spot. Defining success that way would have made the
project's own research question unaskable.

So the criteria above are about **rigour and answerability**: can the
comparison be made on equal terms, is it reproducible by someone else,
and does every number trace back to the code that produced it. Against
those criteria a low cross-dataset score is a *result* — evidence that
detectors do not transfer between the two populations of fake review —
and the failure mode the criteria are designed to catch is the opposite
one: an impressive number that turns out to have come from a leaked
vectoriser, an unbalanced accuracy figure, or a test set the model had
already seen.

That failure did occur, in Week 5, and was caught (#7). Catching it is
the strongest single piece of feasibility evidence in this document,
because it shows the criteria are doing work rather than describing what
already happened.
